# Prior art: one human directing many coding agents across repositories

Researched 2026-11-24. Every claim carries its URL. "Fetched" means the page itself was read; "excerpt" means only a search-result snippet of that page was seen; "unverified" means no primary source was reached.

## Summary for people

- Two isolation styles dominate. Worktrees, which are cheap, are used by Claude Squad, Conductor, vibe-kanban and Claude Code's own background sessions. Containers or VMs, which are safer and duplicate the environment, are used by Sculptor, container-use, Sandcastle, Codex cloud, Jules and Copilot.
- A queue with "ready" semantics is the coordination layer: GitHub issues (Copilot, Jules, OpenHands), Linear's delegate/agent-session model, or a local tracker (Beads). Humans keep ownership and agents act as delegates.
- Hosted agents get their own identity, push to one branch only, cannot approve or merge, and by default cannot trigger CI without a human click.
- On attention, the most concrete patterns are Claude Code's agent view (a "needs input" queue across background sessions) and Anthropic's always-on agent primitives (event inbox, deferred approvals, outbox).
- Critiques agree that review is the bottleneck, and that coding parallelises less well than research.

## (a) Orchestrating many sessions in parallel

- **Gas Town** (Steve Yegge; open source, MIT): a "Mayor" agent coordinates the work. Its other parts are *rigs* (one per repo), *polecats* (workers with a persistent identity and throw-away sessions), *convoys* of tasks, and *hooks* (git-worktree storage that survives crashes). A *Refinery* is a per-rig, Bors-style merge queue, so "polecats never push directly to main". The human uses `gt mayor attach`, `gt feed`, `gt dashboard` and `gt escalate` for blockers. It needs tmux, and also offers a Docker Compose sandbox mode. Fetched: https://github.com/gastownhall/gastown. Yegge's Medium post says v1.0 was released on 2026-04-03 (excerpt only): https://steve-yegge.medium.com/gas-town-from-clown-show-to-v1-0-c239d9a407ec. The original "Welcome to Gas Town" post (January 2026, excerpt): https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04. Yegge reportedly says most developers should not use it; that is secondhand and unverified.
- **Beads** (`bd`): an issue tracker and memory for agents, described as a "distributed graph issue tracker for AI agents, powered by Dolt". `bd ready` lists unblocked work and `bd update --claim` claims it. Hash IDs avoid merge collisions, and old closed tasks are compacted to save context. It works without Gas Town. Fetched: https://github.com/gastownhall/beads
- **Claude Squad** (`smtg-ai/claude-squad`): a Go terminal UI that runs Claude Code, Codex, Gemini, Aider and others, each in a tmux session plus a git worktree. Seen only in a README excerpt and aggregators: https://raw.githubusercontent.com/smtg-ai/claude-squad/main/README.md
- **Conductor** (conductor.build): a Mac app that runs Claude Code, Codex and Cursor agents in parallel in "isolated workspaces", then reviews and merges their work. Its landing page does not say "worktrees". A comparison page excerpt mentions worktrees and Claude Code's `--worktree` option. Fetched: https://www.conductor.build/
- **vibe-kanban** (BloopAI): a kanban board that gives each card an agent workspace with its own branch, terminal and dev server, plus inline diff comments that go back to the agent. The README now says "Vibe Kanban is sunsetting". Bloop shut down on 2026-04-10, and the project continues as fully local and community-maintained. Fetched: https://raw.githubusercontent.com/BloopAI/vibe-kanban/HEAD/README.md, https://www.vibekanban.com/blog/shutdown
- **Sculptor** (Imbue): "Every agent runs in its own container". *Pairing Mode* syncs a container's work into the local repo in both directions. Imbue argues against worktrees because each one needs its dependencies installed again. It supports Claude Code, and Codex since 2025-12-03. Fetched: https://imbue.com/sculptor/ (published 2025-09-26, updated 2026-04-30).
- **container-use** (Dagger): an MCP server that gives each agent its own container and git branch, with the operation history kept in git notes. Excerpt only: https://container-use.com/introduction, https://dagger.io/blog/agent-container-use
- **Sandcastle** (Matt Pocock, TypeScript): `sandcastle.run()` starts agents in sandboxes. The options are bubblewrap or Seatbelt, Docker or Podman, and cloud sandboxes (Daytona, E2B, Fly Sprites, Modal, Vercel). It is meant for "parallelizing multiple AFK agents" and review pipelines. Fetched: https://raw.githubusercontent.com/mattpocock/sandcastle/main/README.md
- **CodeLayer** (HumanLayer): a desktop app for running several Claude Code sessions in parallel. Aggregators only, unverified: https://jimmysong.io/ai/humanlayer
- **Claude Code itself:**
  - *Agent view* (`claude agents`, research preview) lists all background sessions. Each one moves into its own worktree under `.claude/worktrees/` before it edits anything. Claude is told to commit and push the branch and "Never" to push to main, force-push or merge. A supervisor process keeps sessions running with no terminal open. Fetched: https://code.claude.com/docs/en/agent-view
  - *Agent teams* (experimental): a lead plus teammates with a shared task list (file-locked claims and dependencies) and JSON mailboxes under `~/.claude/teams/…/inboxes/`. Teammates' permission prompts surface in the lead session. A message from another agent can never count as the user's approval. There is one team per session, `/resume` does not restore teammates, and token use is "significantly more". Fetched: https://code.claude.com/docs/en/agent-teams

## (b) Issue tracker as the coordination layer

- **GitHub Copilot coding (cloud) agent:** the agent is started from an issue or a task, and "only users with write access" can trigger it. A session on Actions runs for at most 59 minutes, and Copilot works "only on one branch at a time and can open one pull request per task". Fetched: https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent, https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations
- **GitHub Agent HQ / mission control** (2025-10-28, Kyle Daigle): one "command center" to assign, steer and track agents from Anthropic, OpenAI, Google, Cognition and xAI. It runs on Actions or self-hosted runners and works across github.com, VS Code, mobile and the CLI. It adds a control plane for administrators, "branch controls" over when CI runs, and "identity features". Fetched: https://github.blog/news-insights/company-news/welcome-home-agents/
- **Linear agents:** an agent is installed as an app user (`actor=app`). Assigning an issue to it makes the agent the *delegate*, and the human stays the assignee. Agents cannot be project leads. Delegating or mentioning the agent creates an *Agent Session* whose state is visible to users and updated from the agent's activities. The agent should emit a `thought` within 10 seconds. Fetched: https://linear.app/developers/agents; best practices: https://linear.app/developers/agent-best-practices
- **OpenHands resolver:** a `fix-me` label or an `@openhands-agent` comment on an issue or PR starts an attempt to resolve it. The older flow opened a draft PR on success and pushed a branch on failure. The standalone repo was archived on 2024-12-02, and the resolver now lives in the OpenHands repo. Excerpt: https://docs.openhands.dev/openhands/usage/run-openhands/github-action
- **Google Jules:** setup (clone, VM, dependencies) runs first, then Jules presents a plan for approval, then it opens a PR. Each task runs in its own cloud VM. Excerpt: https://jules.google/docs/review-plan/; out of beta 2025-08-06 (TechCrunch): https://techcrunch.com/2025/08/06/googles-ai-coding-agent-jules-is-now-out-of-beta. Picking up an issue labelled "jules" is reported by a secondary source only and is unverified.
- **Devin, Sweep:** Devin's docs were seen only in an excerpt (https://docs.devin.ai/integrations/gh). Sweep was not checked: unverified.

## (c) Agents acting under their own bot identity

- **GitHub Apps vs. user tokens:** GitHub Apps have fine-grained permissions and short-lived tokens. An App installed on an organization "is not dependent on a user" and "does not consume a GitHub seat". Its rate limit scales with the number of repositories. The page does not discuss machine users at all. Fetched: https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app
- **Copilot:** "commits are authored by Copilot", with the requester as co-author, and the commits are signed. It can push to one `copilot/` branch only. It "cannot mark its pull requests as Ready for review and cannot approve or merge". By default, workflows do not run until a person with write access approves them. Fetched: risks-and-mitigations URL above. Since 2026-03-13, administrators can skip that approval, and the docs warn this lets unreviewed code reach secrets (changelog, excerpt): https://github.blog/changelog/2026-03-13-optionally-skip-approval-for-copilot-coding-agent-actions-workflows/
- **Linear:** the app-actor token stands for the app user, not a person; see (b).
- **Devin:** the docs reportedly suggest a dedicated GitHub user account that owns both the commit identity and the credentials Devin pushes with (excerpt only, unverified in full): https://docs.devin.ai/integrations/gh
- **Claude Code agent teams:** messages between agents are marked as coming from another session, and no agent can grant consent for the user. Fetched: agent-teams URL above.

## (d) Sandboxes and VMs, and how credentials are kept out

- **Claude Code sandbox:** OS-level filesystem and network isolation, using bubblewrap on Linux and Seatbelt on macOS. It applies to every subprocess. The docs note that without network isolation an agent could send SSH keys out. The same isolation ships separately as `@anthropic-ai/sandbox-runtime`. Excerpt: https://code.claude.com/docs/en/sandboxing, https://anthropic.com/engineering/claude-code-sandboxing, https://github.com/anthropic-experimental/sandbox-runtime
- **Codex cloud (legacy docs):** the setup script runs with internet access, and the agent phase runs without it by default. Access can be opened per environment with a domain allowlist and, as recommended, GET/HEAD/OPTIONS only. The page gives a prompt-injection example: a hidden instruction in an issue that sends a commit out. It does not say how secrets are provided. Fetched: https://learn.chatgpt.com/docs/cloud/internet-access. A forum post says secrets exist only during setup (unverified): https://community.openai.com/t/codex-cloud-secret-injection/1263867
- **Copilot firewall:** on by default with a recommended allowlist. It covers only the processes the agent starts through its Bash tool, not MCP servers or setup steps. Excerpt: https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall
- **E2B:** one Firecracker microVM per sandbox, each in its own cgroup and network namespace. Excerpt: https://raw.githubusercontent.com/e2b-dev/infra/main/README.md. Vercel warns that API keys passed in as environment variables can be read and sent out by the generated code (excerpt): https://vercel.com/kb/guide/vercel-sandbox-vs-e2b
- **Simon Willison, "Designing agentic loops"** (2025-09-30): the risks of YOLO mode, and the advice to scope *credentials*, not just commands, giving test or staging credentials with spending limits. Excerpt: https://simonwillison.net/2025/Sep/30/designing-agentic-loops/

## (e) Human attention: inbox, approvals, context, cost

- **Agent view:** sessions are grouped as Needs input, Ready for review, Working and Completed. *Peek* shows "the exact question it's asking, above the reply input", so the human can answer without reading the transcript. The terminal tab shows a count such as "2 awaiting input". Fetched: https://code.claude.com/docs/en/agent-view
- **Anthropic, "Building always-on agents"** (William Hu, 2026-11-13): five primitives, which are an event inbox, timers, memory, permissions and an outbox. A tool call that needs approval *ends the run*, and the human's answer comes back as an inbox event that resumes it. Meanwhile the worker handles other events. The outbox advice is "start quiet and then earn more of the user's attention". Fetched: https://claude.com/blog/building-always-on-agents
- **Keeping reports out of the main context:** Anthropic's research system has subagents write their output to external storage and return "lightweight references", which avoids a "game of telephone". Fetched: https://www.anthropic.com/engineering/multi-agent-research-system
- **Long-running work:** a progress file plus git history lets a fresh session pick up where the last one stopped. Excerpt: https://anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Cost ceilings:** Gas Town has a "Scheduler" that limits dispatch capacity (fetched repo). The agent-teams docs say cost "scales linearly" with the number of teammates and suggest starting with 3–5. No tool found enforces a dollar ceiling across sessions; this gap is unverified, not a confirmed absence.
- **HumanLayer:** an SDK through which agents ask humans for approval over Slack or email. Its channels and current status are unverified (aggregators only): https://www.ycombinator.com/companies/humanlayer

## (f) Lessons and critiques

- **Anthropic research system** (2025-06-13): multi-agent setups use about 15× the tokens of a chat. Vague briefs led to duplicated work and gaps. "Most coding tasks involve fewer truly parallelizable tasks than research". The lead waiting synchronously on its subagents is a bottleneck. Fetched (URL above).
- **Simon Willison, "Embracing the parallel coding agent lifestyle"** (2025-10-05): "I can only focus on reviewing and landing one significant change at a time." He runs parallel agents for research, explaining code, small maintenance and tightly specified work. He uses fresh checkouts in `/tmp` rather than worktrees, and wants local agents in containers. Fetched: https://simonwillison.net/2025/Oct/5/parallel-coding-agents/. Later posts:
  - "Recovering lost code" (2026-02-19), on "parallel agent psychosis": he lost track of which branch, worktree or cloud instance held a feature. Excerpt: https://simonwillison.net/2026/Feb/19/recovering-lost-code/
  - On Cursor's planner/worker run with hundreds of agents (2026-01-19): https://simonwillison.net/2026/Jan/19/scaling-long-running-autonomous-coding/ and Cursor's post https://cursor.com/blog/scaling-agents (both excerpt only).
- **Maggie Appleton on Gas Town** (early 2026): Gas Town is "poorly designed" but useful as design fiction. When agents write the code, design and judgement become the bottleneck: "These are the kind of decisions that agents cannot make for you." It burns "thousands of dollars a month". Fetched: https://maggieappleton.com/gastown
- **Matt Pocock:** the Sandcastle README is verified (see (a)). I found **no primary source** for a written retro about sub-agents in worktrees. A secondary summary describes his loop as grill, spec, tickets, implement, review, retro (unverified): https://www.dandoescode.com/blog/matt-pococks-skills-choosing-the-right-workflow
- **Studies of agent-authored PRs:** the AIDev dataset (Li, Zhang, Hassan; arXiv 2507.15003, 2025-07-20) covers more than 456k PRs by Codex, Devin, Copilot, Cursor and Claude Code. Agents work faster, but their PRs are accepted less often, which the authors call a "trust and utility gap". Fetched abstract: https://arxiv.org/abs/2507.15003. A follow-up finds that "reviewer abandonment" is the most frequent reason for rejection (excerpt): https://arxiv.org/pdf/2601.15195

## Patterns that recur

1. **One isolated workspace per agent, one branch per agent, nothing pushed to main.** Merging goes through a human or a merge queue (Gas Town's Refinery, Copilot's single `copilot/` branch, agent view's "never merge").
2. **Durable task state outside the conversation.** Beads/Dolt, the agent-teams task list, Linear agent sessions, GitHub issues, and progress files. A crashed or restarted session picks the work up from there.
3. **"Ready" queues with dependencies and claims** (`bd ready`/`--claim`, file-locked task claims, Linear's delegate).
4. **The human keeps ownership; the agent is a delegate with its own identity** (Linear's assignee vs. delegate, Copilot as author with the human as co-author, GitHub App or dedicated account).
5. **CI and secrets gated behind a human** (Copilot's "Approve and run workflows", branch controls in Agent HQ).
6. **Egress allowlists and setup-only credentials** rather than trusting the agent (Codex cloud, the Copilot firewall, E2B, Claude Code's sandbox).
7. **A needs-input queue plus deferred approvals**, so that one blocked agent never blocks the human or the other agents (agent view, the always-on inbox and outbox).
8. **Reports by reference, not inline** (subagents write to files and the lead receives paths).
9. **Review capacity, not agent count, is the limit** (Willison, Appleton, AIDev's acceptance gap).

## Relevance to the maintainer's pain points

- **Several threads crowding one chat:** run one background session per thread (agent view or Claude Squad style) instead of one chat. Each thread keeps its own context, and the human sees only the needs-input rows.
- **Sub-agent reports landing in the main log:** have sub-agents write their reports to files or tracker comments and return only a path, the "lightweight references" pattern.
- **Approvals and cost ceilings slipping between threads:** make approvals *deferred events* in one inbox (the always-on pattern), not prompts buried in a session. No cross-session dollar-ceiling tool was found, so this probably still needs the maintainer's own hook or budget file.
- **Separate sessions on one checkout getting in each other's way:** use a worktree per session (Claude Code's default for background sessions, under `.claude/worktrees/`) or a container per session (Sculptor, container-use, Sandcastle, or devvm VMs). Worktrees do not isolate ports or databases.
- **Issue watcher needing restarts:** Claude Code's background sessions run under a supervisor process that outlives the terminal. Gas Town keeps state in hooks and Beads so restarts are cheap. Linear and GitHub push work to the agent through webhooks or sessions instead of having it poll. An event inbox with deduplication and retry, as in the always-on post, is the documented design.
- **Bot identity and "only the principal's text counts":** this is consistent with prior art. Copilot gates on the person who triggers it having write access, Linear keeps the human as assignee, and Claude Code treats messages from other agents as never being the user's consent. A GitHub App would add short-lived tokens and use no seat, at the cost of the setup it requires.

## Quarterdeck, read against this setup (2026-11-24, main session)

Read: the README, `.claude/rules/guard.md` and `standing-session.md`, `mcp/src/tools/trusted.ts` and `issue_read.ts`, `core/src/goal-tick.ts` (limits), at commit `fe71f33` of `shannonbay/Quarterdeck` (plugin version 0.32.0, Apache-2.0). Read only: nothing was installed or run.

What fits:
- A goal's run is a background sub-agent of a Claude Code session; the guard plugin's `prompt.submit` hook drops the run's hand-back, so "its report goes to the Goals pane, not your chat" (README; guard.md, #114).
- Watches: a command that lists what is there now, run every few minutes outside the model; a new line starts a run that is told what is new. Webhooks, schedules and a failing health check are the other triggers.
- Each action category is *off*, *propose* (default) or *auto*, enforced by the guard plugin outside the model; a run cannot approve its own proposals. Proposals wait under "Needs you" in a pane, and reach the phone through Remote Control.
- Outside text marks a run, and from then on *auto* acts as *propose*; the mark carries through memory and run summaries; hidden text (HTML comments, invisible characters) is replaced by visible markers. Three probing refusals trip a run.
- Issue pipeline: triage (labels only) → the person picks → refiner (a spec the person approves) → fixer (works in its own clone, proposes push and pull request) → reviewer. Labels serve as the trust signal, since only people with triage rights can set them.
- A standing session keeps goals running with no window open: on Linux, a detached tmux session plus a systemd user timer, in auto mode for permissions.
- Each run shows its tokens and time; `limits.max_run_minutes` (default 15) ends long runs.

What does not fit as it stands:
- Trust is GitHub's `author_association` of OWNER, MEMBER or COLLABORATOR (`trusted.ts`). On the bot's fork the bot is the owner, so its own text would count, against the rule that only the principal's logins count (uellue-bot/skills#3 point 8; `author_association` is relative to the fork, `design/requirements.md`, topic ledger 324).
- One SQLite database per machine (`~/.quarterdeck/tasks.db`), one session at a time runs goals: one VM per project gives one Quarterdeck per project, with no view across them.
- The fixer pushes and opens pull requests on the goal's own repository (`origin`); the upstream pull request from the fork, which the bot's token cannot open, is not covered.
- Goals are recurring background jobs; interactive work with the principal (an interview, a build with review) stays in the chat, apart from a to-do list whose items are brought back with Ask, Plan or Start.
- No ceiling on spend: tokens are shown per run, limits are in minutes.
- Command rules match command names, "so a script that pushes for it gets past them; running goals in a sandbox is on the roadmap" (README).
- Maturity: "built and used daily by one person, on Windows"; Linux spiked on WSL2; the guard depends on how Claude Code delivers a hand-back ("seen in Claude Code 2.1.3xx transcripts"), which may change. Node.js 22.13 or newer.
