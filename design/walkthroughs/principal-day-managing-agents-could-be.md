# Walk-through: a day of the principal managing agents, as it could be

Persona: the manager (`design/stakeholders.md`), here the principal, directing 15 to 20 workstreams across about 10 projects. Confidence: interviewed; needs proposed by the agent as leans and confirmed or corrected by the principal in the chat, 2026-11-24, quoted where they said it in their own words.
What exists: the day as it is now, `design/walkthroughs/principal-day-managing-agents.md` (annoyances A1 to A17, what works W1 to W6); `design/requirements-workstreams.md` (ledger 326). Walked on paper; nothing to run yet.
Needs, not a design: **N** a need, with the annoyance or strength it answers. How each is met is decided later.

## Steps

1. **Evening mission, morning check-in** (A3, A4, A8, A9, A17, W6).
   - **N1** Before handing out missions: "an overview which projects do have candidates for such missions", "a list of good proposals I can adjust or just approve", and "what blocks which workstream at the moment".
   - **N2** In the morning, the same view with "a recap of what came of it": one list of all workstreams across machines and VMs, each named by what it is about, with its state and what is wanted from the principal.
   - **N3** "a quick notification if there's a small thing I could do to unlock, but not if it turns into 1 h Q&A."
   - **N4** Answering and checking without "SSH and screen juggling".
   - **N5** The shape of a check-in: "check in, understand the state, unlock things for maybe 30 min, dump ideas, and then leave things running so I can continue in the office." What makes it long today: the agent's many questions and the principal getting drawn in, "taking a lot of questions and answers until a stretch is unlocked."
   - **N6** Where the check-in happens is not a requirement: "quick and easy is the requirement. Terminal is an instance of 'on the laptop'. … This is an implementation detail."
   - **N7** Spare capacity used without asking, on work without big consequences: "churning a bit on open LiberTEM issues in the background -- some research, running some tests, cooking up options -- and posting these as issue comments somewhere. Ideally without big consequences and therefore without needing approval." Preparing a pending release is allowed: "hallway testing the UI, look for regressions, link check, consistency checks between code and documentation."
   - **N8** Never without the principal (their words):
     - "Things that burn a LOT of tokens that I would have needed elsewhere -- blowing through a weekly limit leaving me stranded for the main work, blowing through a 5 h limit so I can only continue work in the afternoon."
     - "Things that bother third parties or generate a lot of noise, incl for me -- don't spam my inbox, please!"
     - "Otherwise interfering with normal work -- excessive resource use."
     - "Things with real world impact that is hard to ignore or undo -- deploy to production, cut a release, merge a PR other than just mechanical updates like pre-commit, dependabot, conda-forge updates with trivial fixes such as dependencies and Python versions. These actions only after being tested well and hardened, and specifically 'perma-approved' for a repo."
   - **N9** Results in baby steps: "I wouldn't like to be greeted with a 100 files, 10k lines PR from a background job. Ideally the result is easily reviewable and approvable. Better to go in baby steps, such as 'improve type hints in this small sub area'."
2. **Ideas and input from others** (A5, A10).
   - **N10** Dropping an idea or a message in seconds, from wherever the principal is, without choosing a project or a session first (confirmed).
   - **N11** The agent proposes where it belongs; the principal confirms or corrects in a word; it is filed in a fitting form (confirmed).
   - **N12** An idea with no fitting workstream still gets a place (confirmed).
   - **N13** Colleagues are not senders into the principal's pipeline: "I'd rather have them manage their own pipeline, and it then appears as an issue that I'm CC'd in if it concerns me."
   - **N14** Reusable tooling, so that others can work the same way: "maybe we could work to make the tooling nicely reusable, so more people start working together in a compatible way? Btw this also touches that other people have other work styles and processes."
   - **N15** No hurry, a pipeline instead: "no immediate polling. It moves down the pipeline for as long as it can within the rules, gets perhaps prepped with some background research and a set of questions/proposals, and then goes into the appropriate workstream(s) as a work item. So it 'pops up' in the right place."
   - **N16** A short routing confirmation: "sth like 'received well, posted as an issue comment in XYZ', or 'background research started, will appear as a PR in project HKL for your review when done.'" The form is an example: "Not a requirement to be issue comments or PRs, just examples what a routing confirmation could feel like."
3. **Working through the day across machines** (A1, A2, A6, A7, A13).
   - **N17** At most two workstreams talk to the principal at a time; the others hold their needs in the queue of N3, in order (confirmed). The order is all: "only the order is fine", nothing is held back by force.
   - **N18** Switching into a workstream shows a short recap: what it is, where it stands, what is asked (confirmed).
   - **N19** A workstream is reached without knowing which machine, VM or container holds it (confirmed).
   - **N20** Credentials: "both an inventory and less credentials would be great. A bit of a hot topic though -- we better get that one right!" Handled by existing tools, not by code of ours: "Ideally not handle credentials much, not add own features / code / ... that handle credentials, but use existing tools and infra in a smart way. E.g. gh handling the GitHub token, not Claude etc." The model that works: "the Firefox password manager. TONS of different credentials, one place across all my devices, each credential with a very limited scope (no password reuse). I think we can look at that as an example of credential management that works in practice."
   - **N21** Text to take elsewhere (commands, pull request text, links) copies cleanly (confirmed).
   - **N22** A workstream's files can be looked at in a native tool without knowing which machine they are on (confirmed).
4. **Trying out, reviewing, and what the agent may see** (A11, A12, A14, A15, W1 to W5).
   - **N23** While the principal tries a prototype, what they see and do reaches the agent without copy and paste; they choose per moment what is shared (proposed; not contradicted).
   - **N24** Pause, mark a spot, comment; the comment reaches the agent tied to that spot (proposed; not contradicted).
   - **N25** Nothing from the screen leaves the machine unseen, "…or running in an environment, such as GUI in a remote desktop session, that is 'clean' so one can just take from it without review?"
   - **N26** Review of any artifact with comments anchored in place: "yes, inspiration are inline comments in code review."
   - **N27** Per project, what the agent may see; with private data, a filtered copy or a recreated scenario: "yes exactly." An idea for it: "a sort of MCP server inside a modama / crawler deployment that works with models and providers approved for private data, such as blablador, on the inside, and reports sanitized stuff to an outside controlling / reporting agent. That brings it closer to W5 while maintaining a barrier." Who decides what the agent may see, for modama and the crawler: "I'm sort of the steward, so I decide on behalf of the users and the institute, and confer with my leadership and colleagues on that topic." Related, in `uellue/modama` branch `crawler`: MA2 in `python/crawler/design/requirements-operations.md` (an MCP server on staging that enforces read-only access to agreed subtrees), O28 and O29 in `python/crawler/design/working-with-agents.md` (barriers crossed by an editing step; an assistant on the person's side that applies the filters).

5. **Approving** (A16).
   - **N40** An approval reaches the principal as one prepared decision (what and why, what was checked, the exact act), answered in a word, and bound to exactly that act: a changed act asks again (agreed 2026-11-24).
   - **N41** Where the principal approves matters less than proof that it was them; only their text counts. GitHub for minor acts once a security analysis shows that authentication, roles and barriers hold, and for major ones too, later: "we can also include GitHub for major actions once the analysis is solid and I overcame my subjective aversion. After all, releasing a project on PyPI which I trigger from GitHub is pretty major already, with potentially serious, serious consequences (supply chain compromised). GitHub is doing a lot with 2FA and whatnot in that direction, so it may actually be safer as a platform than anything we cook our own." (principal, 2026-11-24).
   - **N42** Every approval logged (who, what, when); standing approvals per repository and kind of act, listed, revocable; they stay until revoked "and get reviewed during housekeeping" (N39; principal, 2026-11-24).
   - **N43** Until the security analysis is done, anything beyond minor acts is approved in the chat, as today (agreed 2026-11-24).

## From the comparison with the record of 2026-11-16 (`design/research/workstreams-mapping.md`)

- **N28** How much goes to the manager, at what size, and what they review is a setting per manager, not a fixed rule: "size and what goes in and what not is an adjustment parameter for the agent alignment -- how much detail someone wants, what they review and what not. So sth that should probably be customizable." A change reaches every agent working for that manager: "It would be great if an adjustment is then forwarded across all agents interacting with that manager! Some *.md file in today's world probably?" (principal, 2026-11-24; answers the tension between N17 and a work-in-progress limit.)
- **N20, refined.** Two related but separate things: "a credential manager that also manages the credentials only I control, and an 'authorized officer' that manages access to credentials and actions that need 'four eye principle' among agents. Kept separate and hardened to avoid stuff 'leaking' or being changed in normal agent development." Which tools, decided in the security analysis of A16 (principal, 2026-11-24).
- **N27, amended.** A sanitised report from an agent inside a deployment gets a check of its own, since information crossing a boundary is biased and distorted (research note, Tushman; principal: "yes, let's add that", 2026-11-24).
- **N29** Where things live is part of the specification: not "a monstrous monorepo 'all things concerning uellue', but a meaningful structure that fosters development, testing, maintenance, collaboration and reuse." The routing of 2026-11-16 (R1 to R16) is reopened once everything is on the table (principal, 2026-11-24).
- **N30** Independent review before the principal's look (O5): every result a workstream hands to the principal for review has had an independent review first, with its report attached; the principal sees the findings and how they were answered and decides whether to look deeper ("that about describes it!"). Specs too: "I'm wondering if agents should review and challenge a spec. I'd guess yes, same reason why they review code and I don't." A different model for the reviewer wherever it saves the principal's time and attention: "Tokens were rarely the limit in practice, except when cooking skills." (principal, 2026-11-24).
- **N31** The principal's limits (N8) and settings (N28) hold for every agent at every point of a session, including after a context summary; where a check can enforce them, it does (O1; principal: "yes, that fits", 2026-11-24).
- **N32** Diagnostics across the network, ending in a debrief: agents push back when far from their working point (O39), and more generally "a meta topic of diagnostics being collected, evaluated and acted upon in that network. Sth like an agent being able to raise sth like an 'Exception' that is seen upstream or by some monitoring agent, and ends up in a sort of debrief. Debriefs have been super powerful, so we should be able to do sth like that across the entire system." (principal, 2026-11-24). Agreed the same day: an exception goes to a collector, not to the principal; the collector groups it and feeds the debrief, and interrupts the principal only for what blocks a workstream now (as N3); "In the future even with self-adjustment if it is obvious enough what to do." Sub-agents may push back against the agent that controls them: "Crew Resource Management for agents, if you will." Measured, to be tried: the principal's minutes per merged change and decisions asked per day, so the debrief can tell whether a change helped (O10, O14; "yes let's try!").
- **N33** One writer per area, many readers and reviewers (O3; "yes"), with workspaces added as needed so that independent work runs in parallel without getting in each other's way (problem 1.1: sessions sharing a checkout, contention between workstreams).
- **N34** A fresh session per area or task, its state in a notes file (O2): "yes, I've been winding down and restarting sessions more often now, and it works better in my subjective impression. Developed a habit to sync and cleanly wind down a session so nothing gets lost."
- **N35** One accountable person per agent; bots never speak as a person (O20, O30; "yes!").
- **N36** Lessons become checks, rules or skills that load by themselves (section 7; "exactly!").
- **N37** A reuse check before building, as part of the independent review (O32 to O37): "yes, and doing that well is a project in itself. We should decide where that should go. Subjectively it intersects a lot with kaizen, but not sure -- in particular the large 'pre-cooked' prior art library!" Where it lives: with N29.
- **N38** Agents and people know what exists across projects (O16, O17 as one way): "What is a requirement is that the agents are coordinated, know what is there and what is what, how to act and interact, and that humans also have that overview." Not a duplicate of the requirements files: possibly generated from devcontainer, devvm, `requirements.txt` and the like; a high-level portfolio description such as libertem.github.io may help. "These are all implementation details."
- **N39** Housekeeping (O14): open work, worktrees and changes "should bubble up in the list. Also as candidates to drop -- that is also a valid choice. Avoid endless sprawl of ledgers, dead issues etc. However, sometimes it is good that sth can lie around for a bit until the right moment to pick it up comes." LiberTEM's release checklist has housekeeping steps already.
- **N44** (from the maintenance walk, `design/walkthroughs/libertem-maintainer-maintenance.md`) Before an agent runs commands, downloads or opens a file from someone else's report, a check asks whether that makes sense and what could happen; if harmless-looking steps could compromise a system through the project, that is a finding of its own, reported to the principal first, as with hyperspy/rosettasciio#457. Reusable for any project: "LiberTEM is an example here" (principal, 2026-11-24).
- **N45** (same walk) Breakage is found before someone trips over it: a scheduled CI run against the newest dependencies in each repository, an agent trying the fix, the result in the morning recap ("sounds like a good idea!", principal, 2026-11-24).
- **N46** (same walk) Heavy runs are not started out of nowhere: a dedicated CI machine is fine for them, but "agents kicking off expensive, heavy runs out of nowhere, in particular if they try to rerun failed jobs or just start the next one, has already triggered me to temporarily deactivate someone's SSH key until I could reach them in chat." (principal, 2026-11-24). So heavy runs go where they are expected, failed runs are not retried in a loop, and someone affected can stop another person's agent without revoking its access.
- **N47** Existing tools, linked: "I'd really like to use existing tools wherever possible, and just link them together in a smart way. Not cook a whole lot of code." (principal, 2026-11-24). A principle for every need above, as N20 already says for credentials.
- **N7, amended.** Background results are tried first in a dedicated space, then forwarded by the principal, and only later posted directly, in spaces we control: "While we test only in dedicated space, and we forward, and then we move to spaces that we control." (principal, 2026-11-24; answers the conflict with posting outside the team, O30 and O23.)
